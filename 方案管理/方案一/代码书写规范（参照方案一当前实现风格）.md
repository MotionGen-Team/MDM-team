# 代码书写规范（参照方案一当前实现风格）

## 1. 文档定位

本文档用于统一本仓库后续开发时的代码书写风格，优先参照当前方案一代码的实际写法，尤其适用于以下内容：

- `model/plan_one/` 下的模块开发
- 与方案实现直接相关的 `visualize/`、`data_loaders/` 适配代码
- 后续方案二、方案三等结构实验代码

这份规范不追求“大而全”，重点是让团队在继续迭代时：

- 文件边界清楚
- 注释风格统一
- 输入输出接口稳定
- 小实验容易替换、容易回滚、容易排查

## 2. 文档存放规范

当前仓库中的文档目录建议按下面方式区分：

- `方案管理/方案一/`
  - 放方案一相关的设计文档、接口文档、实现方案、结构图、代码规范
- `logging/`
  - 放按日期记录的改进日志、实验记录
- `所有开发文档/`
  - 放跨方案通用、且不绑定某个具体方案的标准文档

由于这份代码书写规范当前明确参照的是“方案一当前实现风格”，因此应统一放在：

```text
方案管理/方案一/
```

如果后续需要再抽象出一份不依赖具体方案的全局规范，再另行放入 `所有开发文档/`。

## 3. 总体原则

### 3.1 先保证可维护，再追求结构花哨

第一版代码优先满足：

- 可读
- 可测
- 可替换
- 易定位问题

不要为了让结构“看起来复杂”而牺牲模块边界和排错成本。

### 3.2 一个模块只做一类职责

每个子目录和文件都应有明确边界，不要把多个层级的逻辑混写到同一个文件里。

参照方案一当前结构：

- `shared_embedding/` 负责共享嵌入与输入适配
- `local_branch/` 负责局部结构建模
- `global_branch/` 负责全局时间建模与 summary 注入
- `tcn_refine/` 负责融合后的输出修正

### 3.3 实验优先保持接口稳定

后续改结构时，优先保持模块输入输出 shape 不变。实验重点应放在模块内部，而不是频繁改总装接口。

优先改这些内容：

- 卷积核大小
- dilation
- attention 形式
- pooling 方式
- fusion 方式

尽量不要在小实验里改动模块签名和主链路。

## 4. 文件组织规范

### 4.1 按功能拆文件

推荐方式：

- 一个目录对应一个子模块
- 一个文件对应一类清晰职责

例如当前方案一的 `local_branch/`：

```text
local_branch/
    body_groups.py
    group_pooling.py
    multi_scale_temporal.py
    group_attention.py
    local_branch.py
```

各文件职责清楚：

- `body_groups.py`
  - 只放 body group 定义和切分逻辑
- `group_pooling.py`
  - 只放组内汇聚
- `multi_scale_temporal.py`
  - 只放多尺度时间卷积
- `group_attention.py`
  - 只放组间 attention
- `local_branch.py`
  - 只做总装串联

### 4.2 总装文件只负责串联

以下文件应尽量只负责总装，不堆底层细节：

- `local_branch.py`
- `global_branch.py`
- `mdm_plan_one.py`

这类文件应该让读代码的人快速看出整条链路，而不是在里面反复翻细节实现。

## 5. 命名规范

### 5.1 类名

使用 `PascalCase`，并直接反映职责。

示例：

- `SharedEmbeddingBlock`
- `StructureAdapter`
- `LocalBranch`
- `GroupSummaryBuilder`
- `SummaryFusion`
- `TemporalGQA`
- `FusionBlock`
- `ResidualTCNBlock`

避免使用含义模糊的命名：

- `Block1`
- `TempModule`
- `ModelX`

### 5.2 函数名

使用 `snake_case`，名称直接描述行为。

示例：

- `split_body_groups`
- `build_condition`
- `restore_motion_shape`
- `set_text_encoder`

### 5.3 私有模块或内部辅助类

只有在明确“只在当前文件内部使用”时，才使用 `_` 前缀。

示例：

- `_TemporalMixer`
- `_TemporalConvBranch`

## 6. 注释规范

### 6.1 注释统一用中文

当前团队沟通以中文为主，因此以下内容优先写中文：

- 文件头说明
- 类注释
- `forward(...)` 的输入输出说明
- 关键实现步骤解释
- 后续可替代结构提示

### 6.2 注释不只写“做什么”，还要写“为什么”

参照方案一当前风格，复杂模块的注释至少要说明：

- 这一步在干什么
- 为什么当前先这么设计
- 为什么暂时不采用更复杂的做法
- 后续可以怎么替换

推荐写法：

```python
# 这里先做 mean pooling，而不是 learned pooling。
# 原因是第一版优先保证局部分支稳定、可解释、易排查。
# 如果后面确认简单平均不足，再替换成带权汇聚。
```

### 6.3 对复杂张量变换必须解释

出现 `permute / reshape / view / transpose` 时，尽量补一行注释说明：

- 输入 shape 是什么
- 变换后 shape 是什么
- 这样变换是为了适配哪一层

推荐写法：

```python
# [T, B, G, C] -> [B * G, C, T]
# 把每个结构 token 当成一个独立样本，统一沿时间维做 Conv1d。
```

### 6.4 复杂模块要写出“后续可替换方向”

对于以下模块，建议在实现里直接注明后续可尝试的结构：

- temporal conv
- group attention
- summary fusion
- GQA
- residual TCN

这样队友后面做小实验时，不需要重新猜设计空间。

## 7. Shape 书写规范

### 7.1 关键模块必须写清输入输出 shape

推荐在类注释或 `forward(...)` 注释里写清：

```python
"""
输入:
    h_global: [T, B, D]
    s_t:      [T, B, 3, D]

输出:
    h_global_enh: [T, B, D]
"""
```

### 7.2 内部优先统一使用 `[T, B, ...]`

当前方案一内部默认优先使用：

```text
[T, B, ...]
```

只有在以下场景临时变换：

- `Conv1d` 需要 `[N, C, L]`
- `MultiheadAttention(batch_first=True)` 需要 `[N, S, D]`

变换完成后，应尽快恢复回统一格式。

### 7.3 输出接口尽量稳定

每个局部模块都应尽量保证固定输入输出形式，例如：

- `multi_scale_temporal.py`
  - `[T, B, D_s] -> [T, B, D_s]`
- `summary_fusion.py`
  - `H_global [T, B, D]`
  - `S_t [T, B, 3, D]`
  - `-> H_global_enh [T, B, D]`

## 8. 各层职责约束

### 8.1 Shared Embedding

只负责：

- 输入结构适配
- 轻量时间混合
- 投影出 `H_struct / H_global`

不要在这一层提前堆过重的全局建模。

### 8.2 Local Branch

只负责：

- body group 切分
- 组内汇聚
- 局部时间建模
- 组间轻量交互

不要在这里直接做完整全局 transformer。

### 8.3 Global Branch

只负责：

- group summary 构造
- summary 注入 temporal tokens
- 轻量全局时间建模

不要把 refine 职责提前混入这里。

### 8.4 TCN Refine

只负责：

- local/global 融合
- base prediction
- 残差修正

不要在这里重新做一遍主干建模。

## 9. 实验改动规范

### 9.1 一次实验只改一个因素

例如：

- 只改 kernel size
- 只改 dilation
- 只改 pooling
- 只改 attention 形式
- 只改 fusion 形式

不要一次同时改多个关键模块，否则结果无法归因。

### 9.2 小实验不改总装入口

以下文件尽量只由主负责人维护：

- `model/plan_one/mdm_plan_one.py`
- `utils/model_util.py`
- `utils/parser_util.py`

这样能把“局部模块实验问题”和“系统接线问题”分开。

### 9.3 改模块时优先保持 I/O 不变

例如：

- 改 `multi_scale_temporal.py` 时，尽量保持 `[T, B, D_s] -> [T, B, D_s]`
- 改 `summary_fusion.py` 时，尽量保持 `H_global + S_t -> H_global_enh`

## 11. 当前推荐风格总结

如果用一句话概括当前最推荐的代码风格，就是：

```text
模块拆分清楚，shape 写清楚，注释解释为什么，小实验只动局部。
```

更具体地说：

- 文件按功能拆
- 类名直接表达职责
- 注释统一用中文
- 复杂实现必须写清设计理由
- `forward(...)` 尽量写清输入输出 shape
- 内部尽量统一使用 `[T, B, ...]`
- 每个复杂模块都要提示后续可替换方向
- 小实验尽量不碰总装入口

## 12. 推荐执行方式

后续团队协作建议默认遵守下面这套节奏：

1. 先在方案文档里确认模块边界
2. 每个人只改自己负责的小模块
3. 改动保持输入输出稳定
4. 给复杂模块补中文注释，至少写清：
   - 每一步干什么
   - 为什么这样设计
   - 后续可以试什么
5. 提交前先跑最小前向或 smoke test

这就是当前最适合本仓库、也最符合方案一实现现状的代码书写规范。
