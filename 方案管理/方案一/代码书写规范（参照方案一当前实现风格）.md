# 代码书写规范（参照方案一当前实现风格）

## 1. 文档定位

本文档用于统一 `model/plan_one/` 相关代码的书写风格，优先参照当前方案一已经落地的实现方式。

适用范围：

- `model/plan_one/` 下的模块开发
- 与方案一直接配套的适配代码
- 方案一相关文档维护

## 2. 当前方案一的结构原则

当前方案一主结构已经基本固定为：

```text
Shared Embedding
-> Local Branch
-> Global Branch
-> Fusion
-> Base Prediction Head
-> Residual TCN
```

当前明确只在两处使用 gate：

- `SummaryFusion`
- `ResidualTCN`

因此后续代码开发要遵守一个原则：

- 优先在模块内部做小改动
- 不轻易改主链顺序
- 不轻易把更多 gate 扩散到其它模块

## 3. 总体代码原则

### 3.1 先保可维护，再谈结构花哨

第一版代码优先满足：

- 可读
- 可测
- 可替换
- 易定位问题

不要为了让结构看起来更复杂而破坏模块边界。

### 3.2 一个文件只承担一类职责

参照方案一当前目录：

```text
shared_embedding/
local_branch/
global_branch/
tcn_refine/
mdm_plan_one.py
```

每个目录和文件都应有明确职责：

- `shared_embedding/`
  负责输入适配与共享表示
- `local_branch/`
  负责局部结构建模
- `global_branch/`
  负责 summary 注入与全局时间建模
- `tcn_refine/`
  负责融合、基础预测和残差修正
- `mdm_plan_one.py`
  负责总装与主链串联

### 3.3 实验尽量只动局部

后续实验优先改这些内容：

- kernel size
- dilation
- pooling 形式
- gate 初值
- 学习率

尽量不要在小实验里同时改：

- 主链顺序
- 模块签名
- 输出 shape

## 4. 命名规范

### 4.1 类名

使用 `PascalCase`，并直接表达职责。

示例：

- `SharedEmbeddingBlock`
- `StructureAdapter`
- `LocalBranch`
- `GroupSummaryBuilder`
- `SummaryFusion`
- `FusionBlock`
- `ResidualTCNBlock`

避免：

- `Block1`
- `ModuleX`
- `Net2`

### 4.2 函数名

使用 `snake_case`，直接描述动作。

示例：

- `build_condition`
- `restore_motion_shape`
- `inject_condition_and_position`
- `split_body_groups`

### 4.3 内部辅助类

只有明确只在当前文件内部使用时，才加 `_` 前缀。

示例：

- `_TemporalMixer`
- `_TemporalConvBranch`

## 5. 注释规范

### 5.1 注释统一用中文

优先使用中文编写：

- 文件头说明
- 类说明
- `forward(...)` 输入输出说明
- 关键 shape 变换说明
- 设计理由说明

### 5.2 注释不仅写“做什么”，还要写“为什么”

复杂模块的注释至少要说清：

- 这一层做什么
- 为什么当前先这么设计
- 为什么暂时不选更复杂方案
- 后面还能怎么替换

### 5.3 shape 变换必须解释

遇到 `permute / reshape / view / transpose` 时，尽量补清：

- 输入 shape
- 变换后 shape
- 这么变是为了适配哪一层

推荐写法：

```python
# [T, B, G, C] -> [B * G, C, T]
# 把每个结构 token 看作一个独立样本，统一沿时间维做 Conv1d。
```

### 5.4 文档和代码口径要一致

如果代码已经改成：

- `SummaryFusion` 带 gate
- `ResidualTCN` 带 gate

那么相关注释、文档、流程图文字都必须同步更新，不能继续保留旧说法。

## 6. Shape 书写规范

### 6.1 关键模块必须写清输入输出

推荐在类说明或 `forward(...)` 说明中写清：

```python
"""
输入:
    h_global: [T, B, D]
    s_t:      [T, B, 3, D]

输出:
    h_global_enh: [T, B, D]
"""
```

### 6.2 内部优先统一使用 `[T, B, ...]`

当前方案一内部默认优先使用：

```text
[T, B, ...]
```

只在以下场景临时变换：

- `Conv1d` 需要 `[N, C, L]`
- `MultiheadAttention(batch_first=True)` 需要 `[N, S, D]`

### 6.3 输出接口保持稳定

局部模块尽量保持 I/O 稳定。

例如：

- `summary_fusion.py`
  - `h_global [T, B, D]`
  - `s_t [T, B, 3, D]`
  - `-> h_global_enh [T, B, D]`
- `residual_tcn.py`
  - `R_in [T, B, 2D]`
  - `-> delta_raw [T, B, C]`

## 7. 各层职责约束

### 7.1 Shared Embedding

只负责：

- 输入结构适配
- 轻量时序混合
- 生成 `h_struct / h_global`

不在这里堆重型全局建模。

### 7.2 Local Branch

只负责：

- body group 切分
- 组内聚合
- 局部时间建模
- 轻量组间交互

不在这里重新做完整全局主干。

### 7.3 Global Branch

只负责：

- group summary 构建
- summary 注入
- 全局时间建模

当前只允许在 `SummaryFusion` 一处体现 gate。

### 7.4 Refine

只负责：

- local/global 融合
- base prediction
- residual 修正

当前只允许在 `ResidualTCN` 输出端体现 gate。

## 8. 实验改动规范

### 8.1 一次实验只改一个关键因素

例如只改：

- gate 初值
- dilation
- kernel size
- pooling
- 学习率

不要一次同时改多个主模块，否则结果难以归因。

### 8.2 小实验尽量不改总装入口

以下文件尽量由主负责人维护：

- `model/plan_one/mdm_plan_one.py`
- `utils/model_util.py`
- `utils/parser_util.py`

### 8.3 如果必须改结构，优先写清“是否改变主链”

新增实验前，先判断：

- 是模块内部参数化变化
- 还是主链路变化

如果只是 gate、初始化、卷积参数调整，应明确写为：

```text
不改变主架构，只调整注入强度或局部实现。
```

## 9. 文档维护规范

### 9.1 方案级改动先同步方案文档

需要同步更新：

- `方案一_实现方案.md`
- `方案一_接口文档.md`
- `方案一_pipeline整理版.md`

### 9.2 流程图文字必须跟当前代码一致

如果当前代码只在两处加 gate，流程图也只写这两处：

- `SummaryFusion`
- `ResidualTCN`

不能在流程图里写成大范围架构升级。

### 9.3 实验记录放到 logging

每次实验至少记录：

- 改了哪些文件
- 改了什么
- 跑了多少 step
- loss 变化
- 是否建议保留

## 10. 当前推荐风格总结

如果用一句话概括当前方案一的代码风格，就是：

```text
模块边界清楚，shape 写清楚，注释讲清原因，小实验尽量不改主链。
```

更具体地说：

- 文件按职责拆分
- 注释统一中文
- 复杂实现解释为什么
- 文档与代码保持同一口径
- gate 只在文档和代码都确认的地方出现
