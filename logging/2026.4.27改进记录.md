### 2. 确认 `text condition / timestep` 原本没有真正注入主干

- `PlanOneMDM.forward(...)` 虽然构造了 `c = build_condition(...)`
- 但原实现里 `c` 只被透传，没有真正参与主干计算
- 敏感性测试结果：
  - 修复前改 `timesteps`，输出差异为 `0.0`
  - 修复前改 `text_embed`，输出差异为 `0.0`

结论：原实现对 diffusion timestep 和文本条件完全不敏感，这是首要问题。

### 3. 确认帧级 positional encoding 原本没有接到主干

- baseline 会对主干时序 token 显式加 `sequence_pos_encoder(...)`
- `plan_one` 原实现只把位置编码用于 diffusion timestep embedding
- frame tokens 本身没有接位置编码

结论：原实现缺少帧位置信息，这是第二个关键问题。

### 4. 核对训练目标和接口一致性

- `cond_mode` 与 baseline 一致：`humanml -> text`
- `text_encoder_type` 一致：`clip`
- diffusion 输出目标一致：`predict_xstart=True`，即预测 `x0`
- 输出 shape 恢复逻辑正确：`[B, 263, 1, T]`

结论：这些项不是当前异常的主因。

### 5. 查实自定义 HumanML 顺序本身没有问题

- 检查了：
  - `dataset/humanml/new_joint_vecs/*.npy`

  - `data_loaders/humanml_custom_utils.py`

  - 强行按官方顺序重排后，误差明显增大

结论：当前训练数据本身就是按自定义关节顺序生成的，自定义顺序不是主因。

## 第三轮改动：怀疑 `h_global` 过弱，尝试替换 mean pooling

### 12. weighted attention pooling 改动

背景：

- 观察到前 `1000-6000 step` loss 仍显著高于 baseline
- 怀疑 `SharedEmbedding` 中 `h_global` 由 `mean pooling` 得到，信息损失过大

修改文件：

- `model/plan_one/shared_embedding/shared_embedding.py`

改动内容：

- 原实现：
  - `pooled = h_struct.mean(dim=2)`
- 新实现：
  - 先用 `global_pool_score = Linear(d_struct -> 1)` 计算每个结构 token 的分数
  - 再对 joint/token 维做 `softmax`
  - 最后用加权求和得到 `pooled`

对应形式：

```text
global_weight_logits = global_pool_score(h_struct)
global_weights = softmax(global_weight_logits, dim=2)
pooled = (global_weights * h_struct).sum(dim=2)
h_global = global_proj(pooled)
```

这是一次最小改动，目的只是替换 `mean pooling`，不改变 Shared / Local / Global / Refine 的总体主链。

## 服务器实验结果

### 13. gate 版 + weighted pooling 的短程结果

服务器返回结果：

- `2000 step loss = 0.27`

同时观察到：

- `summary_gate` 与 `residual_gate` 基本没有明显变化

## 当前判断

### 14. weighted pooling 不是主因

根据 `1000 step = 0.29`、`2000 step = 0.27` 的结果，可以判断：

- 这版不是完全训坏，loss 在下降
- 但下降速度仍明显不够
- `weighted pooling` 只带来了有限帮助，至少不是能解释当前落后幅度的主因

因此：

- `h_global` 的 `mean pooling` 不是核心瓶颈
- `summary / residual` 注入过强也不是当前最像的主因，因为 gate 基本没动

### 15. 当前更像的问题

当前更像是 `SharedEmbedding -> h_struct` 这条结构侧表示本身不够好。

也就是说，问题更可能在：

```text
x_t
-> StructureAdapter
-> temporal mixer
-> input_proj
-> h_struct
```

而不主要在：

- `h_global pooling`
- `summary gate`
- `residual gate`

原因：

- gate 基本没变化，说明后端分支并没有积极接管主线
- loss 仍高，说明上游共享表示本身就可能不够有用

## 接下来打算改的方向

### 23. 当前最优先的结构改动方向

基于 `h_struct` 诊断结果，下一步优先级调整为：

1. 优先处理 `StructureAdapter` 中 root/global 信息的注入方式
2. 暂不继续深挖 `weighted pooling`
3. 暂不继续优先折腾 gate

### 24. 当前最怀疑的具体问题

当前最值得怀疑的是：

- root/global 信息被过强、过平均地注入到所有 joint token
- 这导致不同 body group 的局部差异在共享层就被冲淡
- 最终 `left_leg / right_leg / torso` 在统计上几乎塌成同一种表示

### 25. 当前建议的最小修正方向

下一步优先尝试：

- 不再把 root/global 信息等强复制到所有 joint token
- 改成：
  - 只重点注入 `torso`
  - 或者作为单独 global token 处理

当前更倾向的最小修正版是：

- 先做“root/global 信息只进 torso 优先”的版本
- 不改 Shared / Local / Global / Refine 的总体主链
- 不额外引入新的大模块

### 26. 当前不建议优先做的事

目前不建议继续优先尝试：

- 再换一种 `h_global` pooling
- 再去调 `summary gate`
- 再去调 `residual gate`
- 继续大改 `Global Branch`

因为目前最直接的证据已经指向 `h_struct` 本身。
